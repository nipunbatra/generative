A generator does not learn one answer. It learns a distribution of answers and draws from it.

SPADE / GauGAN, Park et al. 2019, teaser figure: here the variation comes from a style image given to the generator.

This is the key shift from the classifiers and regressors students know: the target is not a single value. For one input there is a whole distribution of acceptable outputs.

Precision: in SPADE these three differ because the authors supplied different style images, not purely random codes. The point stands: one layout, several valid photographs.

What all of these share

Randomness in, a learned network, a sample out

Training means: adjust $\theta$ until the samples look like the data. But what is the loss?

Build 1: the random input. Build 2: a sample. Build 3: an optional condition (a sketch, a class label, a sentence).

The difficulty: there is no target image for a random z. Today's answer is the VAE (an encoder tells us which z belongs to which image). The next lecture's is the GAN (a second network learns to judge).

The condition fixes what; the randomness still decides which one of the many matching outputs you get.

Text prompts are the most familiar condition (text-to-image systems). DiffusionSat conditions on a caption plus metadata: location, date, ground resolution. The substation turns snowy in January; the stadium looks European or American depending on the coordinates.

The 7s come from a conditional VAE trained for this lecture: the one-hot label goes into both the encoder and the decoder. We build the unconditional VAE in Part 7; adding a label is a small change.

Our conditional VAE, all labels at once

The label picks the digit; the random $z$ picks the style

{{cvae_labels}}

Each row: one label $c$, from 0 to 9.

Each column: one random $z$, the same all the way down.

Read down a column: every digit is written with the same slant and thickness. The code $z$ carries the handwriting; the label carries the identity.

Real outputs: 2-number code, trained on binarised MNIST for 25 epochs. Because the label already says which digit, z is free to capture only style. Compare with the unconditional VAE later, where z must also encode the digit.

Same idea today: learn a distribution, then sample from it. Only now the samples are images.

The bars are the actual probabilities from the trained Part 1 model bundled with that lecture ("–" is the end marker). Students have seen this exact chart.

Ask: if we always took the most likely character, would we ever get "aabid"? No: after aab we would stop. Sampling, not taking the argmax, is what makes generation varied.

$$p_\theta(\text{aabid}) = \prod_{t} p_\theta(x_t \mid x_{\lt t}) \qquad -\log p_\theta(\text{aabid}) = \sum_{t} -\log p_\theta(x_t \mid x_{\lt t})$$

Training made this number large for every name in the data. That is maximum likelihood, and it is what we want for images too.

Numbers are the bundled Part 1 model's target probabilities for "aabid". The product is tiny (3.2e-7) because there are many possible names; the log turns the product into a sum of per-step losses, the cross-entropy they already trained with.

Bridge: "Give the data high probability" is the goal for every model today. The difficulty for images will be computing that probability at all.

From names to digits

Two ways to generate a 28 × 28 digit

Today: route B. Two questions: where does $z$ come from, and how do we train a decoder when no one tells us the right $z$?

Route A is exactly the name model with pixels as tokens (PixelRNN/PixelCNN): it works but needs 784 sequential steps per image.

Route B makes the whole image in one pass from a short random vector. The rest of the lecture is about training that decoder. The code values shown, (0.33, −1.99), are the actual code of our running "3".

Route A, the way our name model worked

Predict each pixel from the pixels already drawn

Build 1: exactly the name model, with pixels as tokens: read the 3 previous pixels in raster order and output one probability (ink or paper). Real number from a trained model for this position on our 3.

Build 2: 3 pixels in a row cannot see the row above, so the model has no idea of strokes. Give it the pixels above too (a 7 × 7 window, only the already-drawn half): this is the idea behind PixelCNN.

Route A, trained on MNIST

What these two pixel-by-pixel models generate

context: 3 previous pixels · $\log p(\text{our }3) = {{pixelar_row3.logp3}}$

context: 24 pixels above and left · $\log p(\text{our }3) = {{pixelar_window7.logp3}}$

More context, better strokes. And route A gives an exact $\log p(x)$: just add the 784 log-probabilities.

Both models: one masked convolution plus two 1 × 1 layers, 8 epochs, real samples drawn pixel by pixel (784 network calls per image). Test-set average −log p(x): {{pixelar_row3.test_nll}} nats (3 pixels) vs {{pixelar_window7.test_nll}} nats (24 pixels).

Samples are still poor: 24 pixels see only a small neighbourhood, so long strokes do not join up. Real PixelCNNs stack many layers to see the whole image.
